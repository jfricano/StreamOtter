# StreamOtter V1.2.1: fixes by issue

One entry per issue, #21 to #54. Each says what changed, the regression test that guards it, and the docs it touched. "Fails without the fix" means the test was run with the fix reverted and failed. Release-level wording (CHANGELOG, release notes) is owned by the V1.2 PR and was sent there.

Two fixes change behavior a user can see: **P-6** (#23) tightens a config limit and **P-2** (#21) changes a production error code. Both are marked **Changed** below.

## Protocol and gateway sessions

| Issue | Outcome | What changed | Test (fails without the fix) | Docs |

| #21 P-2 | Fixed. **Changed** | In production, subscribe params that fail the channel's `paramsSchema` are answered `FORBIDDEN`, the same as an unknown channel, so channel and parameter names can't be probed before `authorize`. The trace still records `INVALID_PARAMS`. Development still answers `INVALID_PARAMS` with the failing path. Checks that don't depend on the channel (params not a JSON object, or over `maxParamsBytes`) now run before the channel lookup and answer `INVALID_PARAMS` in both modes. | #22 P-3 | Fixed | Traces of refused handshakes are rate-limited (a burst of 100, then 10 per second); skipped traces are counted in a warning log line, written within a second of the first skip and when the gateway stops. | #23 P-6 | Fixed. **Changed** | The minimum `limits.maxControlFrameBytes` is now 9216 (`MAX_TOKEN_BYTES` + 1024), so a CONNECT frame carrying an 8 KiB token fits when the token is printable ASCII without `"` or `\` (JWT, base64url, hex); a token whose JSON encoding escapes characters can exceed it. A config set between 1024 and 9215 now fails validation with `INCONSISTENT_LIMITS`; such configs already refused large tokens. The default (16384) is unchanged. | `contracts.test.ts` "rejects inconsistent and unknown limits" (yes); `protocol.test.ts` "accepts a token at the 8 KiB cap with maxControlFrameBytes at its minimum" | `V1_API.md` §6 |
| #24 P-8 | Fixed | The transport aborts a per-handshake signal when the connection closes, and the gateway combines it with its shutdown signal, so the `AbortSignal` that `authenticate` already receives fires. The handshake ends at once and is traced `CANCELLED`. An `authenticate` call that ignores the signal keeps its connection slot until it settles or `handlerTimeoutMs` passes, so `maxConnections` still bounds concurrent `authenticate` calls. No public API change. | `access.test.ts` "cancels a pending authenticate when the client disconnects" (yes), "counts an authenticate that ignores its signal against maxConnections after the client disconnects" (yes), "frees a cancelled handshake's connection slot when authenticate's timeout passes" (yes) | `V1_API.md` handshake |
