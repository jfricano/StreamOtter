How StreamOtter is built

Part 1 explains how it works. This page covers how it's built: the code structure, patterns and conventions. In short, it's object-oriented in style but shallow. About 35 small TypeScript classes, each with one job, are wired together through narrow interfaces and hidden behind a couple of factory functions. The core knows nothing about Kafka, Socket.IO or SQLite; each of those sits behind an interface at the edge. It runs on a single Node thread, uses three third-party runtime libraries, and many problems other projects would solve with a framework are solved here with a few hundred lines of plain code.

Functions outside, classes insideUsers get createGateway() and createClient(), which return interfaces. The classes stay internal.
Composition, not inheritanceAlmost nothing uses extends. Classes hold references to each other through interfaces.
A core with plug-in edgesKafka, sockets, SQLite and the quarantine topic are adapters behind interfaces, so tests can swap in fakes.
Few dependencieskafkajs, socket.io and socket.io-client, and that's all. Validation, argument parsing, the UI and storage use built-ins or small homegrown code.

01 · Layout

Repo and build

This is a pnpm workspace with one TypeScript configuration shared by every package.

packages/
  contracts/   types, validators, wire protocol, limits      (0 dependencies)
  gateway/     the server: runtime/ sources/ transport/ failures/ operator/ management/
  client/      browser SDK
  cli/         streamotter dev | start | generate | check | operator …
  streamotter/ all-in-one package that re-exports the five above
apps/workbench/            the dev inspector UI (bundled by esbuild)
examples/order-dashboard/  the reference app
tests/  integration · kafka · kafka-replicated · browser · load · deploy · install
contracts/v1/              type-level checks of the public contract

The source runs directly

  • Every package's exports includes a "streamotter-source" condition that points at src/*.ts.
  • Tests and the dev CLI run with node --conditions=streamotter-source, so Node 24 strips the types and runs the TypeScript as-is, with no build step.
  • This only works because the config enforces erasableSyntaxOnly: no enums, no namespaces, nothing that needs compiling rather than stripping.
package.json scripts · packages/gateway/package.json exports · tsconfig.base.json

Strict TypeScript

  • The compiler runs in strict mode, plus exactOptionalPropertyTypes, noUncheckedIndexedAccess (an array or map lookup might be undefined), noImplicitReturns and verbatimModuleSyntax.
  • Publishing uses tsc -b, which emits dist/ with .d.ts files. Only the workbench is bundled, with esbuild.
tsconfig.base.json · package.json "build"

Dependencies: three, deliberately

  • gateway: kafkajs 2.2.4 and socket.io 4.8.3. client: socket.io-client 4.8.3. contracts: nothing.
  • The JSON Schema subset is a homegrown validator in contracts/src/schema.ts, which rejects unsupported keywords instead of ignoring them. There's no zod or ajv.
  • The CLI parses arguments with node:util parseArgs, and the failure journal uses the built-in node:sqlite.
  • The workbench is plain DOM code with a tiny h() element builder that never parses HTML. It uses no framework.
packages/*/package.json · apps/workbench/src/dom.ts · cli/src/cli.ts:6

Where the code is

  • The gateway is about 10,200 lines, and its biggest files are its hubs: runtime/gateway.ts (1,465), failures/journal.ts (1,205), failures/store.ts (887), sources/kafka.ts (838) and failures/service.ts (836).
  • About half the gateway is V1.1 failure handling (failures/ plus operator/).

02 · What users touch

Public surface: factories that return interfaces

No public API hands out a class. That lets the internals change without breaking anyone.

// packages/gateway/src/runtime/gateway.ts:1455-1465 (abridged)
export function createGatewayRuntime(options, internal = {}) {
  const runtime = new GatewayRuntime(options, internal);
  const gateway: Gateway = Object.freeze({
    start:        () => runtime.start(),
    stop:         (o) => runtime.stop(o),
    revoke:       (r) => runtime.revoke(r),
    resumeSource: async (id) => { await runtime.resumeSource(id); }
  });
  internalsRegistry.set(gateway, runtime.internals());   // a WeakMap, for tests and the CLI
  return { gateway, runtime };
}

A frozen facade

  • createGateway() returns a frozen object with four methods that delegate to a private GatewayRuntime. Users can't reach the runtime or monkey-patch it.
  • The CLI and tests need more access. They get it through @streamotter/gateway/internals, which looks the runtime up in a WeakMap keyed by that facade. So the extra access is opt-in and invisible to normal users.
  • createClient() returns StreamClient typed as the Client interface.
gateway/src/index.ts:18 · runtime/gateway.ts:211-215 · client/src/client.ts:459

Types flow end to end

  • Both factories are generic over a ChannelMap (channel name to contract). So client.subscribe("order", …) type-checks the params and the shape of data.
  • streamotter generate writes those TypeScript types from the project config's JSON schemas, so the browser and the handlers compile against the same contract.
  • All shared shapes (frames, Principal, StreamEvent, error codes, limits) live in @streamotter/contracts, which has no runtime dependencies.
contracts/src/types.ts:22, 68 · cli/src/generate.ts:111, 150
Figure 1 · Architecture style

A core with plug-in edges

The center coordinates subscriptions, routing, budgets and failure decisions. Everything that talks to the outside world, including your own code, plugs in through an interface (blue pills). The repo doesn't use the term, but this is the ports-and-adapters (hexagonal) pattern.

Figure 2 · Classes

The classes and how they connect

These are the 11 classes that do the real work. Methods are real names, trimmed to the important ones. Fields are simplified: some drawn as lists are actually Maps or Sets.

The supporting cast

  • Semaphore (runtime/util.ts:95) caps concurrent snapshot() calls at 32.
  • TokenBucket (util.ts:137) rate-limits each browser's control messages to 20 per second, with bursts up to 40. The operator socket has its own copy (operator/ipc.ts:218).
  • RevocationLog (runtime/identity.ts:64) remembers revoked sessions and subjects, so a revoked user can't sneak back in on reconnect.
  • TraceBuffer (runtime/traces.ts:14) is a ring buffer of recent pipeline events that the workbench reads.
  • TrackedSockets (sources/kafka.ts:62) tracks kafkajs's sockets so shutdown can be forced.
  • WaiterSet (client) backs ready() and reconnect() promises, with timeouts and abort support.

Inheritance, almost none

  • The only real extends are errors: StreamOtterError extends Error (contracts/src/errors.ts:65), plus a few local error types.
  • Shared behavior comes from small objects passed in (a GatewayCore, a host, an owner), not from base classes.
  • So each class can be read on its own: everything it can do is visible in its constructor arguments.
03 · Code conventions

Conventions you'll see everywhere

Truly private state

Internal fields use JavaScript's own #private syntax, not TypeScript's private keyword, so the runtime enforces the privacy, not just the compiler. Public fields are almost all readonly. A class's state can only change through its methods.

e.g. runtime/subscription.ts, session.ts, client/client.ts

Tagged unions instead of flags

Outcomes and options are unions with a kind or ok tag, so the compiler forces every case to be handled. Examples: ProcessOutcome = {kind:"commit"} | {kind:"pause", code, failureClass…}, Source is kafka | fixture, and Result<T> is {ok:true, data} | {ok:false, error}.

sources/types.ts:48-50 · contracts/src/types.ts:289

Errors are values on the wire

Nothing throws across the network. Every reply is a Result, and every error carries a fixed ErrorCode, a retryable flag and a requestId. In-process, errors are StreamOtterError instances with that same shape.

contracts/src/errors.ts:65-71

Validate at every boundary

Anything from outside, whether config, a Kafka record, a browser message or your handler's return value, is checked before use. The checks include plain-object tests, depth limits, byte limits, canonical JSON and revision format. Your own handler output is validated too, which is how the gateway catches a bad map().

contracts/src/primitives.ts · schema.ts · config.ts

Canonical forms

Params are serialized with sorted keys (canonicalJson), so {a,b} and {b,a} become the same routing key. Revisions are decimal strings compared by length and then character by character, so they can exceed JavaScript's safe integer range without losing precision.

contracts/src/primitives.ts:28, 109

Design decisions are numbered

Comments cite decision records, such as “ADR-15A §1” or “WHC-1”, in the docs, so the reason for a tricky line is one lookup away.

e.g. sources/types.ts:82 · runtime/core.ts:23
04 · Concurrency

One thread, no blocking

Everything runs on Node's single event loop. Correctness comes from a few small tools rather than locks between threads.

Ordering

  • A per-source lock made from a promise chain. exclusive(work) chains each record onto the previous one (runtime/gateway.ts:53-67), so a source handles exactly one record at a time, in order, even though everything is async.
  • One frame in flight per subscription. The next frame waits for the browser's receipt, which keeps each subscription's order intact.
  • Epochs. Every reset bumps the epoch, so late callbacks from an abandoned attempt recognize they're stale and do nothing.

Limits that never wait

  • Budgets reserve or refuse. ByteBudget.tryReserve() returns false instead of waiting, and the subscription resets. Kafka is never held up by a browser.
  • The semaphore only gates snapshot calls, which are your code's I/O, never the Kafka path.
  • Timers bound everything external: a 5 s receipt timeout and a 10 s snapshot timeout, with retries backing off 1 s then 2 s.
  • AbortSignal is threaded through so stop() can cancel in-flight work cleanly.
05 · Testing

How it's tested

The tests use Node's built-in node:test with no test framework. There are 70 test files, in layers that get slower and more real.

LayerWhereWhat it exercises
unitpackages/*/testContracts validators, the failure service, the journal, Kafka commit logic, operator IPC and runtime pieces, each in isolation.
integrationtests/integration (30 files)A whole gateway plus real clients over real sockets, fed by the fixture source through a shared harness.ts. This covers the protocol, flow control, slow readers, access, failures, the operator and the CLI.
kafkatests/kafka, kafka-replicatedReal Kafka brokers, including a replicated cluster, for offsets, rebalances and quarantine.
browsertests/browserPlaywright in Chromium: the SDK and the workbench in a real browser.
load / deploy / installtests/load, deploy, installMemory and backpressure under load, running behind Caddy, and installing the packed npm tarballs into a clean project.

The adapter interfaces are what make the integration layer cheap. Most behavior is proven with the fixture source in seconds, and only Kafka-specific behavior needs a broker.

06 · Orientation

Where to start reading

  1. packages/contracts/src/types.ts: every shape in the system, from config to handlers to frames to errors.
  2. packages/gateway/src/index.ts, then runtime/gateway.ts from #process: the record pipeline.
  3. runtime/subscription.ts: the sync state machine (#beginAttempt, admit, #transmit, onReceipt).
  4. runtime/session.ts and transport/socketio.ts: one browser connection, from the socket up.
  5. sources/kafka.ts: kafkajs, offsets, pause and seek.
  6. packages/client/src/client.ts and subscription.ts: the browser half.
  7. Then V1.1: failures/service.ts, operator/service.ts and docs/guides/source-failures.md.
