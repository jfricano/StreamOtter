Using and running it

This page is StreamOtter from the outside, through two people's eyes. The developer writes one config file and four handlers, then calls client.subscribe() in the page. The fixture source and the local workbench let them do all of that before Kafka is involved. The operator runs exactly one streamotter start process under a supervisor, behind the app's reverse proxy, and watches its health endpoint, its logs and, with V1.1, its failure incidents. It summarizes the repo's guides; follow the references for full detail.

01 · Developer

First run: a live page in about ten minutes

This follows docs/guides/getting-started.md. You need Node 24 or later and a browser. No Kafka is required.

  1. Install. npm install streamotter provides the CLI, the gateway, the workbench and the browser SDK.
  2. Scaffold. npx streamotter init . writes streamotter.json (a fixture source, two schemas and one channel), server/handlers.mjs (the four handlers plus sample data) and web/example.ts.
  3. Run in development. npx streamotter dev --config streamotter.json --handlers server/handlers.mjs starts the gateway on :7400 and the workbench on :7401, and prints a one-time token.
  4. Try it in the workbench. Preview a subscription as a sample user, step the fixture forward one record at a time, and follow each record through source → validate → map → queue → commit, then send → receipt.
  5. Generate types. npx streamotter generate --config streamotter.json --out generated writes the channel types and the channelVersions constant.
  6. Let the page sign in. Make authenticate accept one fixed local token for now. Restart dev, because handlers load at startup.
  7. Build the page. Create the client, subscribe, render data, and show the state. The page's origin must be listed in allowedOrigins.
  8. Break it on purpose. Step the fixture forward and the page updates. Stop dev and the page turns stale, keeping its last data. Start dev again and it re-snapshots and goes live.

02 · Developer

Into a real app

This follows docs/guides/existing-app.md, using the guide's order-status example, trimmed.

1. Describe the view in streamotter.json

"sources": { "orders": { "kind": "kafka", "topics": ["orders.status"],
  "consumerGroup": "shop-streamotter", "generation": "orders-1",
  "connectionRef": "cluster", "codec": "json", "startFrom": "latest" } },
"channels": { "orderStatus": { "version": 1, "source": "orders",
  "paramsSchema": "OrderParams", "payloadSchema": "OrderState",
  "handlersRef": "orderStatus",
  "delivery": { "kind": "state", "overflow": "resync" } } }
  • The schemas use a small subset of JSON Schema. Check them with streamotter validate.
  • Kafka credentials are referenced through environment variables ({"env": "KAFKA_PASSWORD"}), never written into the file.

2. Publish revisions through an outbox

  • Add a version column, and increment it in the same transaction as each change.
  • Publish the full new state, keyed by entity, through a transactional outbox.
  • Represent a deletion as a status. No tombstones.

That's the whole data contract. The Guarantees page explains why each rule matters.

3. Write the four handlers

authenticate({ token, signal })  → principal | null
  // your session check; tenantId comes from here
authorize({ principal, params }) → true | false
  // may they see this order?
snapshot({ principal, params })  → { revision, data }
  // read your database
map({ record })                  → [{ tenantId, params, revision, data }]
  // Kafka record → rows
  • Pass each handler's signal into your queries, so late results are ignored cleanly.
  • Compile the handlers to JavaScript. The CLI refuses .ts files.
  • The handlers run inside the gateway's process, so they need access to your session store and data, directly or over an internal API.

4. Subscribe from the browser

const client = createClient<AppChannels>({
  getToken: () => session.getAccessToken() });
const order = client.subscribe("orderStatus", {
  channelVersion: channelVersions.orderStatus,
  params: { orderId } });
order.on("data",  ({ data })  => render(data));
order.on("state", ({ state }) => showFreshness(state));
order.on("error", err => showError(err));
  • Treat any state other than live as “may be out of date”.
  • Behind the same-origin proxy, no origin option is needed. A React hook is described in the client package guide.

5. Handle access changes

  • Update your own permission data first, so a reconnect can't bring access back.
  • Then either let the session's short expiry end delivery, or call gateway.revoke({kind: "session" | "subject" | "channel", …}) for an immediate cut-off.
  • revoke is programmatic only. To use it, run the gateway from your own Node process with createGateway() rather than streamotter start.
guides/existing-app.md §7

6. Swap the fixture for Kafka

  • The topic needs JSON values keyed by entity, with one dedicated consumer group per source that nothing else shares.
  • Choose an explicit startFrom for a new group.
  • Change generation whenever topics are recreated.
  • dev can run against plaintext Kafka. Production requires TLS, optionally with SASL.

04 · Operator

Operating it

Start and stop

  • Startup waits up to 30 s for every source to join its consumer group, and rolls back if one doesn't.
  • SIGTERM stops it gracefully within 10 s.
  • After a crash, Kafka keeps the dead instance in the group for about 30 s, so restart after a short delay. An immediate restart may fail once.
  • Production refuses fixture sources, plaintext Kafka and missing secret environment variables, with exit code 2.
DEPLOYMENT.md “Start”, “Keep it running”

Health and logs

  • --health adds a loopback-only listener. Use /health/live to decide restarts and /health/ready for alerts.
  • Readiness reasons are starting, source-held, source-unavailable, journal and quarantine. Liveness stays true through a Kafka outage, so the supervisor won't restart-loop the gateway.
  • Logs are single lines on stdout and stderr, with source IDs and redacted positions, and never payloads or credentials. Pass a logger to createGateway to route them elsewhere.
DEPLOYMENT.md “Health checks”, “Deployment boundary”

Tuning

  • Every limit can be overridden under limits, and validation rejects inconsistent combinations. The full table is on the Guarantees page.
  • The usual adjustments:
    • raise maxDataFrameBytes for large states;
    • raise snapshotTimeoutMs or lower maxConcurrentSnapshots to protect a slow database;
    • raise maxConnections for more users.
  • The defaults are starting points, not capacity claims.
DEPLOYMENT.md “Resource limits”

Unsticking a paused source

  • Without V1.1: fix the cause (data or handler code), then call gateway.resumeSource(id) from code, or restart. A restart is safe because the bad record is still uncommitted.
  • With V1.1: streamotter failures list, then show, then repair. Then sources retry-current, or let quarantine continue if the policy allows.

05 · Operator · V1.1

Turning on failure handling

This is optional. Without a failureHandling section, the gateway behaves exactly like V1.

  1. Choose a policy for each source. pause is the V1 behavior. quarantine-hold copies the record as evidence and stays held. quarantine-resync copies it and continues, but only for invalid-json and payload-schema failures, and only with a recovery guard in your handlers.
  2. Create the journal once. sudo -u streamotter npx streamotter init --failures --config streamotter.json --state-dir /var/lib/streamotter/shop. The directory must be owned by the gateway's user and not writable by anyone else, on a persistent volume. It needs Node 24.15 or later.
  3. Provision the quarantine topic yourself. Set max.message.bytes to at least maxSourceRecordBytes plus 80 KiB, and grant the gateway's Kafka user the extra permissions it needs.
  4. Start with the extras. streamotter start … --state-dir … --operator-socket --health 127.0.0.1:7402.
  5. Acknowledge the boundary in snapshots. After continuing past a record, every snapshot on that source must return the boundary's ID until it's retired.
  6. Back up journal.sqlite and its -wal file together, with the gateway stopped. Never delete WAL files on their own.

06 · Both

When something's wrong

Start from what you see. Every SDK failure is a StreamError with a code.

What you seeMost likely causeWhat to do
FORBIDDEN “This origin is not allowed.”The page's origin isn't in allowedOriginsAdd the exact scheme, host and port, then restart. Wildcards aren't allowed.
auth-required / UNAUTHENTICATEDauthenticate returned null, the token expired, or getToken failedFix the session check. After the user signs in again, call client.reconnect().
FORBIDDEN after connectingauthorize said no, or the channel, version or params are wrongUse the generated channelVersions. In development, the Inspect tab shows which check failed.
Stuck staleThe source is paused, Kafka is down or rebalancing, or a snapshot is missing the recovery boundaryCheck the log and the readiness reasons. With V1.1, run failures list.
resync-requiredThree automatic attempts failed, often from snapshot timeoutsCall subscription.resync(), for example from a retry button. Look into how slow snapshot is.
OVERLOADEDA subscription, connection or rate limit was reachedCheck the limit named in the message (Guarantees page).
Exit 1, “Sources did not become ready”A broker, credentials or topic problem, or a restart right after a crashRead the staged diagnostics printed below the error. Right after a crash, try again.
Exit 2 at startupInvalid config, a fixture or plaintext Kafka in production, or a missing environment variableThe message names the path and the fix.
