Guarantees and limits

StreamOtter makes one central promise: a view is never silently wrong. A browser view is either live, meaning it caught up to the source with nothing missing, or it says so with stale or resync-required. Everything else follows from that promise. Revisions never go backwards. A bad record is never skipped quietly. A slow browser never stalls Kafka. Access is checked when a view starts, again before its snapshot is sent, and on every frame. This page lists what is promised, what is deliberately not promised, what happens in each failure, and every limit, with its source in the spec or code.

Honest stateA view is either live or visibly not. StreamOtter never keeps reporting live while it drops data.
Never backwardsRevisions only increase in a browser's lifetime. Duplicates are harmless, and older states are thrown away.
Nothing skippedA bad record pauses its source, uncommitted. Moving past it takes evidence or a person.
Bounded and isolatedEvery queue has a byte limit, and every frame is checked against the user's tenant, expiry and revocations.

What StreamOtter promises

02 · Non-promises

What it deliberately doesn't promise

These are stated in the spec, not discovered gaps. Knowing them is most of what makes the promises above believable.

No exactly-once browser delivery. The founding document rules it out explicitly. Browsers get the latest state, and duplicates are ignored.
A Kafka commit isn't proof of delivery. The offset commits once a record is queued for its browsers, before any browser receives it. A lost frame is repaired by a fresh snapshot, not by Kafka.
No history or replay. A browser that was away gets the current state, not the updates it missed. Retained event channels are V2.
live isn't a promise of freshness. It means caught up with the source while the source is healthy. It doesn't say how recent the data is, or that your UI drew it.
A receipt isn't a render. A receipt means the SDK validated the frame and handed it to your listener. The SDK doesn't wait on promises your listener returns.
It can't fix your data. If your database and your topic disagree, for example because a change was saved but never published, StreamOtter can't tell. That's why the outbox pattern is required (section 05).
One gateway only. There's no clustering in V1. Two gateways on one consumer group would each deliver only part of the data.
Total memory isn't capped. Budgets cap queued frames, not Node's total memory or kafkajs's buffers.
The defaults aren't capacity claims. The spec calls them “starting bounds”. One measured workload is published (section 07).

04 · Security

Security model

Who you are, and what you can see

  • The token goes in the Socket.IO auth payload, never in the URL. It must be non-empty and at most 8 KiB. Your authenticate handler decides who the user is; the gateway never trusts the browser's claim.
  • Allowed origins must match exactly, with no wildcards, and production rejects a missing origin. The origin check supplements authentication; it doesn't replace it.
  • Unknown channel, wrong version, denied access and (in production) bad params all return the same FORBIDDEN. A probing browser learns nothing about which channels exist.
  • Revocation works per session, per user or per single channel and params, and the gateway remembers it so a reconnect can't restore access.
V1_API.md §7 · §13 V1.2.1 · guides/existing-app.md §7

What stays on the server

  • Kafka credentials never leave the server. Browsers subscribe to channels you define, never to topics.
  • Handlers are your trusted code, loaded at startup. Config can't contain code, and nothing is uploaded at runtime.
  • Public error messages never reveal topic names, secrets, stack traces or protected payloads. Logs are redacted.
  • Production refuses plaintext Kafka, fixture sources and the management server. The workbench exists only in development, on loopback, behind a per-run token.
  • The V1.1 operator socket is protected by file permissions plus a token file. Anyone who can read the state directory is an operator.
  • Every input has a size limit: tokens, params, control messages, source records and data frames.

05 · Shared responsibility

Your side of the contract

The guarantees above depend on these rules about your data. StreamOtter can't check them for you.

Every change gets an increasing revision

A decimal string of up to 39 digits that only goes up for each entity and never resets, not even after the entity is deleted and recreated. A version column incremented in the same transaction as the change works well.

One entity, one partition

Key each record by entity, so one view's changes arrive in order on one partition.

Full state, no tombstones

Each record is the whole new state. Represent a deletion as a status in the state, such as "deleted". A null record pauses the source.

Database and topic agree

Every change your snapshot can return must also reach the topic, so publish through a transactional outbox or equivalent. Otherwise a view can miss a change and never know it.

07 · Evidence

What's verified, and what isn't

Kafka

  • Verified with kafkajs 2.2.4 on Apache Kafka 4.1.2:
    • connection modes: TLS with a supplied CA, and TLS with SASL PLAIN or SCRAM-SHA-256/512;
    • bad credentials, untrusted CAs and missing topics fail at the right stage without leaking secrets;
    • poison records pause without being skipped;
    • after a crash, redelivered records never move the displayed state backwards;
    • rebalances and outages turn views stale, and they recover.
  • V1.1, verified: byte-exact quarantine, and advancing past a record even when the gateway is killed on either side of the commit. Quarantined copies survived the leader broker being killed on a 3-broker cluster.
  • Not verified: TLS with the system trust store, other Kafka versions, managed Kafka services, brokers with ACLs enabled, and network partitions.
guides/kafka.md “What is verified”

The one measured load

  • Setup: 200 clients, plus 10 deliberately stalled clients, receiving 600 records fanned out to 6,000 frames.
  • Results:
    • All views were live in 99–148 ms.
    • The source committed every record in 22–26 ms, without waiting for the stalled clients.
    • Every client converged, in order, in 201–267 ms.
    • Peak queued bytes were 2.39 MB, against the 64 MiB limit.
    • All stalled clients were disconnected.
  • This was one process over loopback. The docs call it bounded-behavior evidence, not a capacity claim.

Confidence

What's inferred rather than read

  • The headline promise, “a view is never silently wrong”, is my summary of V1_API.md §5–§6 (“Never silently switch to data dropping while still reporting live”). The spec doesn't use that phrase as a slogan.
  • The “user sees” column of the failure matrix describes the SDK's states. What a person actually sees depends on how the app renders stale.
  • The client backoff and token refresh timing come from my earlier reading of client/src/client.ts, not from a spec table.
