## Acceptance and rollback

For preview and production: test links, assets/fonts/logo, menus, dark mode, canonical/Open Graph URLs, 404, and expected response content types. Check `deployment.json` matches source/run. Workflows append response headers to the accepted build: nosniff, X-Frame-Options DENY, CSP frame-ancestors 'none', and strict-origin-when-cross-origin referrer policy. This limited CSP permits the existing inline theme/navigation code; it is not a full script policy. Preview also sends noindex. Verify actual deployed headers on `/` and nested routes; local files don't prove Pages behavior.

Docs: check guides and anchors, generated API navigation and View source URLs at the selected release tag, repository/spec links, Under the Hood HTML/relative assets, `/sitemap.xml` and robots metadata. Generate declarations with root `pnpm build` before docs build. Check the API docs against that same source release; do not mix current main declarations with old-tag links.

Blog: deployment sets **BLOG_DRAFTS=0** and never 1. Check `/rss.xml` is valid RSS with the production self link, `/sitemap.xml` matches only published content, and drafts are absent from HTML/feed/sitemap. No posts exist at the prepared source: “No posts yet” and an empty RSS channel are expected. Actual launch content remains an editorial owner decision, not an invented placeholder post. Canonical/feed URLs are blog.streamotter.dev even on preview. Blog imports docs global styles, so check fonts/assets again on each candidate.

Rollback restores a previously accepted deployment within the affected project only, then verifies identity, HTTPS and links. Do not roll back npm, demo/backend, apex/www, or peer projects. Preserve domain attachment; first-launch withdrawal needs explicit owner direction if there is no accepted predecessor.
