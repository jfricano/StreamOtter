How it works

StreamOtter is one Node process that turns Kafka records into live, per-user state in the browser. Your code supplies four handlers: authenticate a token, authorize a subscription, map a Kafka record into full-state rows keyed by tenant, channel and params, and snapshot the current state from your own database. The gateway reads Kafka one record at a time, runs map, routes each row to the browsers subscribed to that exact key, and commits the Kafka offset once the row is queued. Every browser subscription starts from a snapshot and then receives only newer revisions. When anything goes wrong (slow reader, dropped socket, overflow, expired token) the gateway throws the queue away and re-snapshots, which is safe because every frame is a whole state and never a delta. V1.1 adds a durable failure journal so a bad record can be held, quarantined and, under strict guards, stepped past instead of stalling the source forever.

Full state, never deltasEach frame replaces the last. Dropping frames is always safe; a fresh snapshot repairs anything.
Your app owns the truthSnapshots come from your snapshot handler. The gateway stores no channel state (inferred, see the end).
Revisions guard every hopCanonical decimal revisions, epochs and sequence numbers let both sides reject stale or out-of-order data.
Never skip a record silentlyAn unprocessable record pauses the source. V1.1 only moves past one with quarantined evidence and a recovery guard.

One record, topic to browser

The live path for a record on a Kafka source with a browser already subscribed and live. Line numbers are at commit 1c75aaa.

  1. Kafka adapterThe consumer hands over one message. KafkaJS runs with autoCommit: false and one partition at a time.   2. PipelineRecords on one source are processed strictly one after another. SourceRuntimeImpl.exclusive() chains every process() and any operator redrive onto one promise lock. With failure handling on, the pipeline first checks that the source hasn't moved past a held record without a recorded advance.gateway/src/runtime/gateway.ts:65-69, 632-640, 664-685
  3. PipelineDecode and size-check. Bytes over maxSourceRecordBytes (1 MiB default), invalid UTF-8, invalid JSON, nesting deeper than 16, and tombstones (null values) are all caught before your code sees them. None is thrown away: the record pauses its source, uncommitted, and is reported (see Failure handling below).gateway/src/runtime/gateway.ts:720-739 · contracts/src/limits.ts:12-33

  5. Your codeRun map() for every channel on that source. Each call gets an AbortSignal and a 2-second handlerTimeoutMs. It returns an array (max 100) of MappedState: { tenantId, params, revision, data }.   6. PipelineTurn each row into a routed frame. Only those four fields are allowed. Params are canonicalized against the channel's paramsSchema, the revision must be a canonical unsigned decimal string, the frame must fit maxDataFrameBytes (64 KiB), and data must pass payloadSchema. The routing key is [channel, version, tenantId, canonicalParams].gateway/src/runtime/gateway.ts:880-918 · runtime/core.ts:62-64
  7. PipelineRefuse a revision conflict. If the same key gets the same revision with different data (within this record, or against what a subscriber already holds), the source pauses with REVISION_CONFLICT. Nothing from the record is admitted.gateway/src/runtime/gateway.ts:805-818
  8. SubscriptionsAdmit to every subscriber of that key. Each ServerSubscription drops anything at or below its latest revision, reserves room in its byte budget, queues the frame and pumps. Admission never waits: if the budget is full, that subscription is reset and re-snapshotted instead.gateway/src/runtime/gateway.ts:822-833 · runtime/subscription.ts:188-208
  9. Kafka adapterCommit the offset. process() returns {kind: "commit"}; the adapter resolves the offset and commits offset + 1 through a serialized commit chain. A failed commit is retried in the background and the record may be redelivered, which the revision filter absorbs.gateway/src/runtime/gateway.ts:706-708 · sources/kafka.ts:312-331
  10. SubscriptionsSend one frame. Only one frame per subscription is in flight. It goes out as so:data {subscriptionId, epoch, sequence, event} and starts a 5-second receipt timer.gateway/src/runtime/subscription.ts:486-512
  11. TransportSocket.IO writes it to the WebSocket. WebSocket only, no long-polling, Socket.IO's own connection-state recovery off, inbound frames capped at maxControlFrameBytes.gateway/src/transport/socketio.ts:84-104, 142-160

The commit point. Step 9 happens right after step 8, before steps 10 to 13. A Kafka offset means "the gateway processed and queued this record", not "a browser has it". That is deliberate for state delivery: a browser that misses a frame gets a fresh snapshot from your app (inferred rationale; the code shows the order, not the reason).

Subscription lifecycle

How a subscription syncs

A new subscription, a resync, a reconnect, a source coming back and an overflow all run the same sequence, each as a new epoch. Live updates are captured from the moment the key is registered, so nothing that lands during the snapshot is lost.

authorize()→ wait for source→ new epoch, start capture→ snapshot()→ validate + re-authorize→ send snapshot (seq 1)→ receipt→ drain buffered newer states→ live

Snapshots run under a gateway-wide semaphore (maxConcurrentSnapshots 32) with a 10-second timeout. A snapshot is rejected if it fails the payload schema, regresses below a revision the browser already saw, or, under V1.1 quarantine-resync, doesn't echo the source's current recoveryBoundaryId. After the receipt, buffered updates at or below the snapshot revision are dropped and the rest drain in order. A failed attempt goes stale and retries after 1 s, then 2 s; after maxSyncAttempts (3) it reports resync-required.

Reference

The runtime pieces

Kafka consumption and offsets

  • One KafkaJS consumer per source, one dedicated consumer group per source (validation refuses a shared group), partitionsConsumedConcurrently: 1, auto-commit and auto-resolve off.
  • On a bad record the adapter pauses every topic of the source and seeks back to that offset, so a resume retries the same record. Nothing after it is committed.
  • Startup records "latest" high-water marks before consuming, so a restart doesn't silently skip; out-of-range committed offsets are logged as possible skips.
  • A watchdog marks the source degraded after 12 s without broker activity; status changes push every subscription on that source to stale and back.
  • Sockets are tracked so stop() always releases them; a small KafkaJS 2.2.4 patch fixes an idle timer spin.

Typed state and the mapper contract

  • streamotter.json is a ProjectConfig: connections, sources (kafka or fixture, each with a generation), schemas, channels {version, source, paramsSchema, payloadSchema, handlersRef, delivery: {kind: "state", overflow: "resync"}}, limits, and optional V1.1 failureHandling.
  • Schemas use a deliberately small JSON Schema dialect: string, number, integer, boolean, null, bounded arrays, closed objects.
  • ChannelContract<Params, Data, Version> types both ends: your HandlerRegistry on the server and createClient<AppChannels>() in the browser.
  • Revisions are decimal strings compared by length, then lexically, so they never lose precision.
  • Validation is structural only. It never resolves secrets or connects to brokers, and keys for future features (history, replay, schemaRegistry…) get an explicit "not in V1" message.

Access control

  • The handshake checks the exact Origin against allowedOrigins (required in production), takes only {token, protocolVersion}, caps the token at 8 KiB and connections at maxConnections.
  • Your authenticate returns a Principal {subject, tenantId, sessionId, expiresAt, claims} or null. The session closes itself at expiresAt.
  • Your authorize runs per subscription, and again just before the snapshot is sent.
  • The tenant in the routing key is the verified one, so a row mapped for tenant A can only reach tenant A's subscriptions.
  • gateway.revoke() closes by session, subject or channel. A sequence-numbered RevocationLog also catches revocations that land mid-handshake or mid-snapshot.

Browser delivery and reconnects

  • The SDK owns one connection at a time and turns off Socket.IO's own reconnection; it subscribes again only after an authenticated so:hello.
  • Reconnect delay is full jitter: a random wait up to min(30 s, 500 ms × 2ⁿ), and only while subscriptions exist.
  • UNAUTHENTICATED, FORBIDDEN and protocol mismatches suspend in auth-required until your app calls reconnect().
  • 30 s before the token expires it opens a fresh connection with a new getToken() and swaps it in. If the identity key changes (account switch) every subscription is closed so one user's view never carries over.
  • Control requests time out after 5 s and are never buffered while offline.
client/src/client.ts:184-365 · client/src/connection.ts:24-138 · contracts/src/protocol.ts (timings)

Backpressure

  • A three-level byte budget: subscription (1 MiB, 100 frames) inside connection (4 MiB) inside gateway (64 MiB). A reservation must fit every level.
  • One frame in flight per subscription, released by the browser's receipt; no receipt in 5 s closes the connection.
  • Overflow never blocks Kafka. It invalidates that subscription's epoch, which goes stale and re-snapshots.
  • A socket whose unread output passes the connection budget is force-closed. Control messages are rate-limited (20/s token bucket) and size-capped.
  • What does slow Kafka: your map() and records on one source run in series (inferred consequence of the one-at-a-time design).

Failure handling V1.1

  • Without failureHandling, a bad record pauses its source until someone calls resumeSource(), which retries it (V1 behavior).
  • Nine failure classes. Only invalid-json and payload-schema may be quarantined; mapper errors, routing errors, conflicts, tombstones and oversize records always hold. There is no skip policy.
  • Policies per source: pause, quarantine-hold (keep a verified copy, stay paused), quarantine-resync (copy, then try to continue).
  • Continuing requires an acknowledged quarantine write, a closed circuit breaker (it trips after five distinct incidents are advanced automatically within 60 s by default: automaticAdvanceLimit: { incidents: 5, windowMs: 60000 }), and your recovery guard saying "recoverable". The journal records a recovery boundary first; from then on every snapshot must acknowledge it. Then advancePast() commits offset + 1, reads it back and resumes. Any doubt leaves the record held.
  • The journal is one SQLite file under stateDirectory: WAL with full sync, one transaction per change, an exclusive OS lock. When full it refuses writes; it never evicts.
  • /health/live and /health/ready report reason categories (source-held, journal, quarantine…), never topic names.

Operator and management APIs

  • OperatorApi has ten operations: status, listFailures, showFailure, exportFailure, retryCurrent, reassess, reopenCircuit, retireBoundary, evaluate, redrive. Every change carries an expected revision and is recorded as an operation in the journal.
  • evaluate dry-runs the stored original bytes through the same #prepare as live traffic and returns a plan with a hash of the outputs. redrive re-runs it under the source lock and admits only if the hash still matches. It never commits or seeks.
  • Reached in-process (getGatewayOperator) or over a Unix socket at <stateDir>/run/operator.sock: a token file, one JSON line per connection, rate-limited.
  • The management HTTP API (/management/v1, default port 7401) is development-only: loopback, per-run bearer token, no CORS. createManagementHandler lets a host mount it behind its own session.

Scope

What it deliberately doesn't do

The config validator names these as future work and rejects them with a clear message. They describe the edges of the current design.

No history or replay. Delivery is current state only; retained event channels (delivery.kind: "events"), recovery cursors and replay are V2.
One gateway process. Multiple gateways or a cluster are V2; there is one Kafka connection profile per project.
JSON only. One codec; Schema Registry integration is V2.
Read-only to Kafka. Commands (browser to Kafka) are V3. The only V1.1 write is the quarantine topic.
One transport. Socket.IO over WebSocket.
No skip button. No ignore or discard policy exists; moving past a record always needs quarantined evidence or an explicit operator action.

Confidence

What's inferred rather than read

Everything above with a file reference was read in the code at 1c75aaa. These points are my interpretation.

  • No durable channel state in the gateway. I found no store of channel data in runtime/: only per-subscription queues, the trace ring buffer and the V1.1 failure journal. Snapshots always come from your handler.
  • Why the offset commits before browser delivery. The order is in the code; the reason (full-state frames plus re-snapshot make browser loss harmless) is my reading of the design.
  • Throughput shape. One record at a time per source, awaited through every map(), means the slowest mapper sets a source's pace. That follows from the code but I didn't measure it.
  • Line counts are wc -l over each package's src/*.ts, comments included.
